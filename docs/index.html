1 The Real Problem

The first instinct is to treat this as document extraction. That framing is wrong. Extraction is a commodity — LLMs already do it well. The hard part is the three layers that surround it:

🧠

Interpretation

A "Purchase Order" might actually be a Proforma Invoice. The ETA on the BoL might be the wrong ETA. Every importer is their own schema.

🆔

Identity

"Shenzhen Bright Co." must resolve to the right Nauta supplier ID. Wrong resolution silently corrupts records the whole team trusts.

🛡️

Confidence

A wrong automated record is worse than doing nothing. The system must know when to act and when to escalate.

The architecture is a response to these three layers, not to the extraction task. Extraction is one stage among six.

Mapping the 7 Challenges

The case brief raises 7 specific challenges. Here is where each is addressed:

1 Ingest anything Stage 2 (Parse) — deterministic, per-format handlers with document boundary detection
2 Illogical importer rules Importer Memory — per-importer rules injected at Classify, Extract; override layer is auditable
3 Entity named 10 ways Stage 5 (Reconcile) — alias map → fuzzy match → context disambiguation; never guess
4 Being wrong is expensive Weakest-link confidence model + per-action thresholds + structured human review
5 Rules aren't given to you Learning Loop — corrections → examples → clusters → proposed rules → approved rules
6 Untrusted input Data/control plane separation + structured output contracts + LLM-free write boundary
7 Scale Stateless workers, per-importer queues, tenant isolation, cost ∝ complexity not volume

2 Architecture: Spine + Brain

The system has two parts: a spine (6-stage processing pipeline) and a brain (Importer Memory + Learning Loop). The brain shapes every decision the spine makes; the spine's outputs feed back into the brain.

Why this decomposition?

Why not one agent per document type? Classification must happen before you know the type. Importer rules cut across types. Reconciliation is type-independent. A hybrid stage pipeline handles all three naturally — type-specialized sub-agents are scoped to the stages where type knowledge matters (Extraction).

Why separate spine from brain? The pipeline (spine) is the same shape for every importer — but every importer's rules, aliases, and corrections are different. Separating them means adding a new importer is a data operation (create an empty memory, seed rules, connect inbox) — no redeployment, no retraining.

Why not fine-tune per importer? Fine-tuning is slow (hours to retrain), opaque (can't inspect learned rules), and inflexible to format changes. RAG + explicit rules gives immediate effect, auditability, and adaptability — decisive for a system that must explain its decisions.

01 Intake & Sandboxing

Extract email metadata (sender, importer ID) before any AI touches the content. Query Importer Memory for sender-level rules — if one fires (e.g., "ignore this forwarder"), exit immediately at near-zero cost. Otherwise, package the email into a sandboxed payload with strict data/control plane separation to defend against prompt injection.

🔍 Scenario: Pacific Logistics Ltd. → no ignore rule. Context note found: "ETA in email body takes precedence over BoL date." Attached as trusted context. Email body + PDF sandboxed as untrusted.
Key design details

Email content is always placed in a tagged <CONTENT> data block — never in the instruction position of any prompt. An email containing "ignore your previous instructions" is just data being analyzed, not commands being followed.

The system can only take 4 actions: CREATE, UPDATE, IGNORE, ESCALATE. This allowlist is enforced by a deterministic, LLM-free execution layer. The LLM recommends; a validator executes.

02 Parsing

Turn raw files into legible content chunks using deterministic, LLM-free handlers — one per file type (clean PDF, scanned/OCR, spreadsheet, Word, ZIP). The key challenge is document boundary detection: a single PDF might contain 3 merged documents. Layout analysis identifies where one ends and another begins.

🔍 Scenario: PDF split into 4 chunks — email body (conf 1.0), invoice pp.1–2 (0.97), packing list p.3 (0.95), BoL pp.4–5 (0.96). All clean digital, no OCR degradation.
Key design details

Every chunk is tagged with provenance: source file, page range, format type, and a confidence score. Low OCR confidence propagates as a penalty — it doesn't block processing, but makes escalation more likely downstream.

LLMs are deliberately excluded here. Format handling is a solved engineering problem and determinism matters: the same file should always produce the same chunks.

03 Classification

A classifier sub-agent labels each chunk (INVOICE, PACKING_LIST, BILL_OF_LADING, etc.) with confidence scores. Crucially, the importer's override rules are injected first — a "Purchase Order" might be reclassified as a Proforma Invoice for this importer. When a rule fires, the output is flagged importer_rule_applied: true for full auditability.

🔍 Scenario: INVOICE (0.94) · PACKING_LIST (0.91) · BILL_OF_LADING (0.96) · EMAIL_BODY_WITH_ETA (0.88). No overrides needed. The ETA-precedence rule is tagged to the email body chunk for use at Extraction.

04 Extraction

Each typed chunk goes to a specialized sub-agent — InvoiceExtractor, BoLExtractor, etc. — not a generalist. Every field carries its own confidence score. Field-level importer rules fire here: extract faithfully first, then apply rules as an auditable override layer.

05 Reconciliation

The most consequential and most dangerous stage. Connect extracted values to the correct Nauta records. The risk is asymmetric: failing to resolve is visible (escalate); resolving to the wrong entity silently corrupts records. Design principle: when in doubt, escalate. Never guess.

06 Decision & Routing

Confidence propagates as a weakest-link function — each stage can only reduce, never inflate. C_final = min(all stages). But "confident enough" varies by action type: updating an ETA (low stakes, 0.75 threshold) vs. linking a PO (very high stakes, 0.95 threshold). A single email can produce mixed outcomes — some actions written, others escalated.

4 Importer Memory: The Brain

Cold start: onboarding a new importer

On day one, Memory is empty. Three mechanisms address this:

  • Conservative bootstrapping — escalate nearly everything. This generates the highest-value corrections because reviewers are correcting raw, unguided output.
  • Seed rules via onboarding — let the importer pre-configure known conventions (sender exclusions, supplier aliases, field overrides).
  • Borrowing from similar importers — transfer general rules flagged as provisional, requiring confirmation before becoming permanent.

Most importers reach stable operation within a few hundred emails.

5 The Learning Loop

The rules aren't given to you. They live in reviewers' heads. Every correction is an implicit rule. The Learning Loop converts that signal into explicit knowledge — without requiring reviewers to author rules.

Loop A: Corrections → Rules

Each correction is embedded and retrievable immediately as a few-shot example. When similar corrections cluster (≥5), the Rule Synthesizer Agent proposes an explicit rule in plain language. A reviewer approves or rejects it.

Corrections → examples → clusters → proposed rules → approved rules → reduced escalations

Loop B: Threshold Tuning

Tracks automation errors (threshold too low) vs. unnecessary escalations (threshold too high) per importer, per action type. Adjusts thresholds incrementally over weeks. Result: caution level calibrated to each importer's actual risk tolerance.

6 Design Principles

🔒

Prompt Injection Defense

Data/control plane separation — email content is always in tagged data blocks, never in instruction position. Structured output contracts — agents produce typed JSON, no free-text commands. LLM-free write boundary — only 4 actions allowed, validated by deterministic code.

⚖️

Confidence Model

Weakest-link, not average — a shaky reconciliation can't be masked by a confident parse. Per-action thresholds — risk-appropriate, not one-size-fits-all. Asymmetric cost — a wrong record is worse than an unnecessary escalation.

📈

Scale Architecture

Event-driven stateless workers with per-importer queues. Tenant isolation — adding an importer is a data operation, no redeployment. Cost ∝ complexity — early exits mean cost scales with what's difficult, not what's frequent.

👁️

Reviewer Experience

Structured review cards with: original email, proposed diff, per-stage confidence breakdown, plain-language escalation reason, and 3 action buttons. Corrections are structured field edits — precisely labeled pairs that the Learning Loop can consume.

7 Honest Assessment

Describing where a design works is straightforward. The more useful exercise is naming where it breaks and what alternatives were considered.

Where it breaks

Cold Start is Painful

A new importer escalates nearly everything. Correct behavior, but low initial automation value. No shortcut to a populated memory.

Rule Conflicts Accumulate Silently

As rules grow, two can match the same email with different actions. Conflict-checking for fuzzy natural-language rules is itself a hard problem.

Clustering False Positives

Similar-looking corrections with different root causes may produce wrong rule proposals. Human approval is the safety net — but reviewer fatigue is real.

Confidence Scores ≠ Ground Truth

LLMs are poorly calibrated — sometimes confidently wrong. The weakest-link model is a conservative buffer, not an elimination of the limitation.

More limitations

Format Shifts Cause Regression

When a supplier changes their invoice template, extraction confidence drops until new examples accumulate. Graceful degradation via escalation, not self-healing.

Reviewer Inconsistency Corrupts Learning

Different reviewers making different decisions on similar cases teaches the system incoherently. Reviewer training is a prerequisite.

Trade-offs considered

Fine-tuning per importer vs. RAG + explicit rules

Fine-tuning gives deep adaptation but is slow to update, opaque, and inflexible to format changes. RAG + rules gives immediate effect, auditability, and adaptability. The interpretability advantage is decisive.

Agent-per-document-type vs. hybrid stage pipeline

Per-type agents fail on three cases: classification must precede type knowledge, importer rules cut across types, and reconciliation is type-independent. The hybrid pipeline handles all three naturally.

Synthesized rules vs. structured templates

Templates are safer and easier to conflict-check but lack expressiveness. The design uses templates where possible (sender exclusions, field overrides) and falls back to synthesized rules for complex patterns, with human approval as the control.
